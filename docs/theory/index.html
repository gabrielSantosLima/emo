The one rule

Same state + same inputs = same outputs, at the same time.

Contents

01

Emulation is a timing problem

An emulator is not a simulation of electricity. It is a software model that reproduces the observable behavior of a machine: given the same initial state and the same inputs, it produces the same outputs at the same moments in time. For a game console, the interesting outputs are memory contents, interrupts, video frames and audio samples.

The hard part is not making a CPU execute instructions. The hard part is making every component observe the world in the same order the real hardware does. A write to a video register one scanline too late is a visible glitch. An audio sample generated one step too early is a pop. Emulation is, first and foremost, a scheduling problem.

Accuracy

Does it behave like the hardware?

Cycle counts, bus activity, register side effects, timing of interrupts and DMA. Accuracy is measured against the real machine, not against another emulator.

Compatibility

Does the game run correctly?

The set of software that produces the expected result. It is not the same thing as accuracy: an approximate emulator can run many games, and a precise one can still fail on an obscure edge case.

Performance

Does it fit the frame budget?

NTSC gives roughly 16.6 ms per frame for CPU, PPU and APU work. Every accuracy improvement costs cycles; the skill is spending them where software can observe the difference.

Key distinction

Low-level emulation (LLE) models the actual hardware units and their timing. High-level emulation (HLE) intercepts a known interface and reproduces its result. HLE is faster and simpler, but it tends to break when software uses the interface in an unexpected way. For a from-scratch SNES emulator, start with LLE for the main components.

Finally, determinism is a feature. If the core depends only on emulated time, not on wall-clock time or randomness, then save states, rewind, netplay, automated tests and bug reports all become tractable. Treat determinism as a design constraint from day one.

02

The machine is a clocked system

Every useful unit of time in the SNES is derived from a crystal oscillator. The main oscillator feeds the CPU and the PPU. The audio subsystem has its own oscillator, which is the root cause of most synchronization pain.

Timing explorer

Unit Rate Derivation

A frame is a grid: scanlines stacked vertically, each one divided into dots (PPU pixels). One dot lasts four master cycles. The CPU does not run on dots; it runs on memory accesses that cost 6, 8 or 12 master cycles depending on the region being touched. That is why the CPU is described as roughly 3.58 MHz even though the master clock is 21.48 MHz.

Access type Master cycles Examples
Internal / no bus access 6 Register operations, internal cycles
Fast memory access 8 WRAM, most cartridge ROM
Slow / I/O access 12 PPU, APU and other memory-mapped registers
Design decision

Pick one canonical time unit for the core and derive everything else from it. Most accurate emulators use master cycles (or a normalized nanosecond-like unit) so that CPU, PPU and APU can be compared without floating point. Never use the host clock inside the emulation core.

Dots, scanlines and frames

A scanline is 1364 master cycles, or 341 dots. Only 256 dots are visible in normal resolution; the rest is horizontal blanking. A frame has 262 lines on NTSC (312 on PAL), and only the first 224 (or 239 in overscan) are visible. Vertical blanking is where the CPU is allowed to touch VRAM and OAM freely.

The picture is therefore produced continuously, not all at once at the end of the frame. Registers written while the beam is in the middle of the screen can change the rest of the frame. This single fact drives most of the PPU design.

03

Keeping independent clocks in sync

The CPU and PPU share the 21.477 MHz master clock, so their relationship is an integer ratio and synchronization is trivial. The APU does not: its 24.576 MHz oscillator does not divide the video clock, so the CPU and the SPC700 drift relative to each other unless the emulator actively keeps them aligned.

Relative schedulers

The classic SNES solution is a relative scheduler. Keep a signed 64-bit counter for each pair of components that need to stay in sync. When the CPU runs N cycles, subtract N × f_other. When the other component runs N cycles, add N × f_self. Whichever side is behind gets to execute next. 

// CPU <-> SPC700, NTSC
int64 cpu_smp = 0;

if (cpu_smp >= 0) {
    cycles = cpu.step();
    cpu_smp -= cycles * 24'576'000;   // weight by the SPC700 clock
} else {
    cycles = spc.step();
    cpu_smp += cycles * 21'477'272;   // weight by the CPU clock
}

The same pattern links the SPC700 to the DSP. The SNES needs two such counters: CPU ↔ SPC700 and SPC700 ↔ DSP. The CPU↔PPU pair runs on the same clock, so it can use raw master cycles without scaling.

Granularity

Granularity What runs Trade-off
Per instruction One CPU instruction, then catch up PPU/APU Simple and fast; misses mid-instruction bus effects
Per CPU cycle One memory access or internal cycle Good accuracy/perf balance; the usual starting point
Per dot One PPU pixel (4 master cycles) Needed for mid-scanline effects; much more expensive
Per scanline An entire line at once Fast renderer, but inaccurate for raster tricks

A pragmatic architecture is the catch-up model: the CPU executes a whole instruction, but every bus access advances the PPU and APU up to the current master cycle. It keeps the CPU code simple while preserving the ordering that software can observe.

Common trap

Running the APU in large chunks at the end of a frame is tempting and almost always wrong. Music and sound effects depend on register writes landing at the right SPC cycle, and the DSP reads ARAM while the SPC700 is running. Sync first, optimize later.

04

Memory is the interface

The 65C816 sees a 24-bit address space: 16 MB, split into 256 banks of 64 KB. Almost everything the CPU does is a read or a write through that space, and almost every device is exposed as memory-mapped registers. The bus is the central object of the emulator.

Region Contents
$00–$3F, $80–$BF System area: WRAM mirrors, PPU/APU registers, CPU I/O, DMA registers, joypads
$40–$7D, $C0–$FF Cartridge ROM and SRAM (mapping depends on LoROM/HiROM)
$7E–$7F 128 KB of Work RAM (WRAM)
$2100–$21FF PPU and APU registers (mirrored across banks)
$4200–$43FF CPU control, interrupts, multiply/divide, DMA channels

Reads and writes are not symmetric

Many registers behave differently when read versus written, and some have side effects on every access: writing a data register can increment an internal address, reading a status register can acknowledge an interrupt, and reading OAM or VRAM returns a latched value. The bus API must therefore expose read(addr) and write(addr, value) as operations with behavior, not as array indexing.

Open bus and wait states

Addresses with no device return the last value that was on the data bus, a behavior called open bus. Games do read unmapped regions; returning zero is not always harmless. Access speed also depends on the region: WRAM and most ROM are fast, while PPU/APU registers are slow and cost extra master cycles. The memory map is a timing map too.

Mental model

Build the bus before the CPU. The CPU only needs to ask the bus for bytes and to know how many cycles the access cost. If the bus owns mapping, mirroring, open bus and side effects, the CPU stays small and testable.

05

The CPU: a 65C816 with a 24-bit world

The SNES CPU is a Ricoh 5A22 built around the WDC 65C816. It is source-compatible with the 6502 but adds 16-bit registers, a 24-bit address space, new addressing modes and a native mode with different semantics from the 6502-compatible emulation mode.

Register Width Role
A / B / C8/8/16Accumulator (C is A and B together)
X, Y8 or 16Index registers
S16Stack pointer
D16Direct page base
DB, PB8 eachData bank and program bank
PC16Program counter inside the current bank
P8Status flags: N V M X D I Z C
E1Emulation mode (6502 compatibility)

M, X and E change the instruction set

The M flag selects 8- or 16-bit accumulator/memory accesses; X selects 8- or 16-bit index registers. In emulation mode (E=1), the CPU behaves like a 6502: 8-bit registers, a page-1 stack, and the 6502 interrupt vectors. XCE switches between the two worlds.

The practical consequence is that one opcode has several behaviors. A 256-entry table is not enough: the effective instruction set is closer to 1,280 variants once M, X and E are taken into account. Generate the table or the code from a compact description instead of writing every combination by hand.

Addressing modes

Expect immediate, direct, direct indexed, absolute, absolute indexed, long, long indexed, stack-relative, stack-relative indirect, and several indirect forms. Direct-page and absolute indexing have page-crossing penalties and wrapping rules that differ between emulation and native mode. These quirks are exactly what the CPU test ROMs check.

Interrupts and control flow

Event Trigger Native vector Emulation vector
RESETPower-on / reset$FFEC$FFFC
NMIStart of vertical blank$FFEA$FFFA
IRQH/V timer or external$FFEE$FFFE
BRKSoftware breakpoint$FFE6$FFFE
COPCoprocessor call$FFE4$FFF4
ABORTBus abort input$FFE8—

WAI sleeps until an interrupt, STP stops the clock until reset, and interrupt recognition has a specific cost relative to the current instruction. Games use WAI to wait for vblank, so a wrong implementation shows up as a hang or as an unstable frame rate.

Do not skip

Validate the CPU against instruction-by-instruction test suites before touching video. The SingleStepTests suite gives you the full state and bus activity for 20,000 runs per opcode; the gilyon tests cover the functional quirks on real hardware. This is the cheapest debugging you will ever do.

06

The PPU: pixels on a schedule

The SNES has two video chips, S-PPU1 and S-PPU2. They are hard-wired logic, not programmable processors, and the CPU cannot read back the pixels they generate. The only feedback the CPU gets is through status registers and the H/V counters. That makes the PPU the least documented and most frustrating component to emulate perfectly.

Memory Size Contents
VRAM64 KBTiles, tilemaps, Mode 7 map
CGRAM512 B256 colors, 15-bit BGR555
OAM544 B128 sprites: 4 bytes each plus 32 bytes of high bits

Tiles are bitplanes

A tile is 8×8 pixels stored as separate bitplanes, not as bytes of palette indices. A 2bpp tile uses two planes, a 4bpp tile four, an 8bpp tile eight. Decoding a pixel means combining one bit from each plane into a palette index. Tilemaps then reference tiles by index and add flip, palette and priority bits.

Background modes

Mode Layers Depth Typical use
042bpp eachSimple scenes, four independent layers
134/4/2bppThe most common mode in commercial games
224bppOffset-per-tile effects
328/4bppMore colors, offset-per-tile
428/2bppOffset-per-tile with a low-color layer
524/2bpp512-pixel hi-res mode
614bppHi-res, offset-per-tile
718bppAffine rotation and scaling

Sprites and priorities

OAM holds 128 sprites. Each scanline can display at most 32 sprites and 34 8×8 tiles; exceeding that sets the overflow flags and drops sprites. Sprites support 8×8, 16×16, 32×32 and 64×64 sizes, horizontal and vertical flipping, palettes and priority relative to backgrounds. Priority is not a single number: background layers have a base priority, each tile can raise it, and sprites are inserted at several priority levels.

Mode 7

Mode 7 is the famous affine mode: a 128×128 tilemap is transformed by a 2×2 matrix, with scroll, center point and wrapping/fill rules. It is used for racing games, rotating rooms and the classic SNES "floor" effect. It is still 8bpp tiles, but the tilemap is linear rather than the usual 32×32 layout.

Effects

On top of the layers sit mosaic, two windows with per-layer enable/invert and logic modes, color math (add/subtract, half, fixed color), pseudo-hires and interlace. These are not post-processing filters: they are part of the per-pixel priority and blending pipeline.

Timing is the renderer

The PPU emits one dot every four master cycles: 341 dots per line, 262 lines per NTSC frame. During the visible portion it fetches tiles and sprites; during horizontal and vertical blanking the CPU may access VRAM and OAM. The H/V counters let software synchronize with the beam, and IRQs can fire at a chosen scanline or dot.

A scanline renderer that applies all register changes at the start of the line is a reasonable first target. It will run most games, but raster effects that change scroll, color or windows mid-line will be wrong. A dot-based renderer is the accurate path, at a significant performance cost.

Expect this to be the hard part

Even mature emulators still discover PPU edge cases. Build the PPU with a clear pixel pipeline, keep every register latch explicit, and make it easy to dump VRAM, CGRAM and OAM for comparison against a reference emulator.

07

DMA and HDMA: stealing cycles

The SNES has eight DMA channels. Each channel connects a region of CPU memory (the A-bus) to a PPU or APU register (the B-bus) and can copy a block on demand. DMA is not free: it halts the CPU and consumes master cycles, and the transfer pattern determines the order of reads and writes.

HDMA is the more interesting mode. Instead of one large transfer, each channel reads a small table and performs a transfer at the start of every scanline, optionally indirecting through another pointer. That is how games do per-line gradients, parallax, Mode 7 perspective and window effects without waking the CPU on every line.

DMA

Triggered by $420B

A block transfer that runs immediately. Used for loading VRAM, CGRAM and OAM during blanking.

HDMA

Triggered by $420C

A table-driven transfer that repeats once per scanline. Used for raster effects and mid-frame register changes.

For the emulator, DMA is a timing feature before it is a data feature. It must interact correctly with interrupts, the CPU's halt state, the bus wait states and the PPU's access windows. Implementing it as "copy this array instantly" will break games that depend on when the transfer happens.

08

The APU: a computer inside a computer

The audio subsystem is a separate computer. It has its own CPU (the SPC700), its own 64 KB of ARAM, three timers, a DSP that synthesizes eight voices, and a 64-byte boot ROM called the IPL. The main CPU talks to it through four registers at $2140–$2143, and nothing else.

The boot protocol

On power-on, the IPL clears the first page of ARAM and waits for the main CPU to upload an audio driver. The protocol uses the four communication ports as a handshake: the SPC700 signals readiness, the CPU sends a block and an index, and the SPC700 acknowledges. Only after the driver is uploaded does the SPC700 start executing game audio code.

The IPL ROM itself is Nintendo code. Your options are to require a user-provided dump, use a clean-room replacement with the same protocol, or emulate the protocol at a high level. See the legal section.

The SPC700

An 8-bit CPU with its own instruction set, 1.024 MHz clock, 64 KB address space, PSW flags and a stack. It is simpler than the 65C816 but still has its own addressing modes, timers and I/O ports. It runs the audio driver, sequences music and writes to DSP registers.

The DSP

Synthesis

Eight voices at 32 kHz

Each voice plays a BRR-compressed sample with pitch, volume, ADSR/GAIN envelope, sample loop and optional pitch modulation.

Mix

Echo, noise and stereo

A noise generator, an 8-tap FIR echo buffer in ARAM, and per-voice left/right volume feed the final stereo mix.

BRR (Bit Rate Reduction) stores samples in 9-byte blocks: one header plus eight 4-bit nibbles. The DSP decodes them on the fly, applies the envelope and mixes. The output is 32 kHz stereo; the frontend must resample it to the host rate (44.1 or 48 kHz) with a ring buffer and, ideally, dynamic rate control to avoid underruns and crackles.

Synchronization reminder

The DSP advances with the SPC700, which advances against the main CPU through a relative scheduler. Audio is therefore not a separate "play a sample" subsystem; it is another timed component that must see register writes at the right cycle.

09

Cartridges and coprocessors

A ROM image is not just a blob of code. It has a header at $FFC0–$FFFF (in the ROM's address space) describing the title, mapping mode, ROM size, SRAM size, region and vectors. The two main mapping families are LoROM (32 KB banks mapped into the upper half of each bank) and HiROM (full 64 KB banks). ExHiROM extends the address space further.

The cartridge is also where coprocessors live. Some games put a whole second processor or a math chip in the cart, and the emulator must implement that chip or gracefully refuse to run the game. This is where scope explodes.

Strategy: get the base console right first. Add coprocessors in order of payoff, and decide early whether you want LLE (implement the chip) or HLE (intercept its interface). MSU-1, Satellaview and the Super Game Boy are separate projects, not core requirements.

10

Proving that it works

There is no perfect oracle. Even the most accurate emulator is an approximation, and commercial games exercise only a fraction of the hardware. The practical answer is a layered test strategy: unit tests for pure logic, hardware test ROMs for behavior, frame hashes for rendering, and differential testing against a reference emulator for everything else.

Level 1

Unit tests

Address decoding, flag logic, tile decoding, BRR decoding, scheduler math. Fast, deterministic, no ROM required.

Level 2

Hardware test ROMs

Run on real hardware and on your emulator. Compare register/memory state, not just "it printed PASS".

Level 3

Frame and audio hashes

Run a deterministic ROM, hash the framebuffer or audio buffer at known frames, and fail CI when the hash changes unexpectedly.

Level 4

Differential testing

Run the same input movie in your emulator and in Mesen/bsnes, then compare traces, frames and audio. Divergence points to the bug.

Build the debugger you will need

A disassembler, a trace log with PC/registers/cycles, breakpoints on memory access, and viewers for VRAM, CGRAM, OAM and the tilemaps are not luxuries. They are the difference between finding a bug in minutes and staring at a black screen for a weekend.

Established tools to compare against: Mesen (excellent debugger), bsnes-plus and no$sns.

Debugging order

Never start with a commercial game. Start with test ROMs, then a homebrew that paints a solid color, then backgrounds, then sprites, then scrolling, then audio. Each step gives you a smaller search space.

11

ROMs, firmware, and the legal line

An emulator is legal in most jurisdictions; distributing copyrighted ROMs is not. The emulator should load ROMs provided by the user and must not bundle game images, firmware dumps or keys.

The SNES has no general BIOS, but the SPC700 has a 64-byte IPL boot ROM. It is Nintendo code. The common approaches are:

  • Require the user to supply a dump, like a BIOS file.
  • Ship a clean-room IPL that implements the same protocol, such as snes-spc700-boot-rom.
  • Emulate the boot protocol at a high level instead of executing the ROM.

Coprocessor firmware (DSP-1, SuperFX, SA-1) raises the same questions. This is not legal advice; if the project is distributed commercially, review the licenses and firmware policy with a lawyer.

Glossary

Bus
The shared path through which the CPU reads and writes memory and devices.
Open bus
The last value driven on the data bus, returned by unmapped reads.
Master cycle
The finest common time unit, derived from the 21.477 MHz oscillator.
Dot
One PPU pixel period: four master cycles.
Scanline
One horizontal line of video: 341 dots, or 1364 master cycles.
VBlank
The vertical blanking period where the CPU can safely access VRAM and OAM.
NMI / IRQ
Non-maskable and maskable interrupts used for vblank and raster timing.
DMA
Direct memory access: a block transfer that steals CPU cycles.
HDMA
Per-scanline DMA driven by a table, used for raster effects.
MMIO
Memory-mapped I/O: hardware registers exposed as addresses.
LLE / HLE
Low-level emulation (model the hardware) vs high-level emulation (model the interface).
Dynarec
Translating guest instructions to host instructions at runtime for speed.
Scheduler
The component that decides which emulated processor runs next.
Save state
A serialized snapshot of the entire emulated machine, including timing state.
BRR
Bit Rate Reduction: the SNES compressed sample format.
ADSR
Attack, Decay, Sustain, Release: the volume envelope of a DSP voice.
IPL
Initial Program Loader: the 64-byte SPC700 boot ROM and its upload protocol.
LoROM / HiROM
The two main cartridge-to-address-space mapping schemes.

# Commit and Push

Use this skill when the user asks to commit, commit and push, or ship the changes
currently in the working tree.

## Workflow

### 1. Inspect the repository

```bash
git status --short
git branch --show-current
git diff
git diff --cached
git log --oneline -5
```

- Read the full diff before staging anything.
- Use the recent log to match the repository's commit style.
- If the user named specific files, stage only those files.
- If the working tree has unrelated changes, do not include them. Commit only
  what the task actually changed, or ask which changes belong to the commit.

### 2. Run the project checks

Before committing, run the checks configured for the current stack (formatter,
linter, type checker, tests). Stack-specific commands live in `AGENTS.md` and in
the project manifest once one exists. A failing check blocks the commit: fix the
problem first.

### 3. Stage only the intended files

```bash
git add path/to/file path/to/other
```

- Stage files by explicit path.
- Avoid `git add -A`, `git add .` or `git commit -a` unless every reviewed change
  belongs to the same commit.
- Never stage local planning files (for example `PLAN.md`), secrets, environment
  files, build output, ROMs or firmware dumps.
- Review the staged diff one more time with `git diff --cached`.

### 4. Write the commit message

Follow Conventional Commits, in English, short and imperative:

```text
<type>(<optional scope>): <short description>
```

Allowed types: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`, `perf`,
`build`, `ci`, `style`.

Examples:

```text
feat(cpu): implement 65c816 emulation mode
fix(ppu): latch scroll registers per scanline
docs: add hardware references
chore: ignore local planning files
```

Rules:

- Keep the subject under ~72 characters and do not end it with a period.
- Use the body only when the change needs context (why, trade-offs, references);
  wrap it at 72 columns.
- Never add AI authorship or co-author trailers: no `Co-Authored-By`, no
  "Generated by ...", no tool or agent attribution. The author is the human
  contributor only.
- Never mention the agent, the prompt or the session in the message.

### 5. Commit

```bash
git commit -m "type: short description"
```

- If a hook fails, read the output, fix the cause and commit again.
- Do not use `--no-verify` unless the user explicitly asks for it.
- Do not amend, rebase or squash existing commits unless the user explicitly
  asks for it.

### 6. Push

```bash
git push
```

- Push to the current branch. If it has no upstream, use
  `git push -u origin <branch>`.
- Never force-push (`--force`, `--force-with-lease`) unless the user explicitly
  requests it on a branch they own.
- If the push is rejected as non-fast-forward, stop and report the situation
  instead of rewriting history.

### 7. Verify and report

```bash
git status --short
git log -1 --oneline
```

Report the branch, the commit hash and subject, and confirm the working tree is
clean. If anything was intentionally left uncommitted, say what and why.

## Boundaries

- This skill does not create tags, releases or changelogs. Releases go through
  the `Release` GitHub Actions workflow.
- Do not commit generated artifacts that the repository ignores.
- Do not commit or push when the user only asked to review changes.
